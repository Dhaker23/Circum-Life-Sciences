# ADR-0009: WorkCenter in Phase 3, Equipment in Phase 8 (Execution-Location Phasing)

- **Status:** Accepted (Phase 3, owner-confirmed decision D3)
- **Date:** Phase 3
- **Deciders:** Circum project owner
- **Supersedes:** (none)
- **Related:** `docs/PRD/PHASE-3-IMPLEMENTATION-PLAN.md` §3.3 and §3.9 (D3), `docs/PRD/CIRCUM_MASTER_PRD_FINAL.md` §5 (Operations executed on Equipment by Operators), §10 (Traceability genealogy includes Equipment), §18 (Phase roadmap: Equipment module is Phase 8), `CONTEXT.md` (Phase 3 proposed terms: Work Center), ADR-0007 (multi-site ownership: WorkCenter is site-owned)

## Context

Circum Master PRD §5 states that an Operation is "executed on Equipment by Operators", and PRD §10 includes Equipment in the traceability genealogy. At the same time, PRD §18 places the full Equipment module (the Equipment master with maintenance, calibration, and the `VALID / EXPIRING / EXPIRED / OUT_OF_SERVICE` status model) in Phase 8, not in Phase 3.

Phase 3 builds the production-execution domain: Routing, Operation, Work Order, Manufacturing Batch, Device Lot, Operation Execution, Material Consumption. An `OperationExecution` needs to record where the work physically happened (which station, which line) so that production scheduling, OEE (Phase 10), and the Equipment dimension of the traceability genealogy have a stable reference. But the full Equipment master, with its maintenance schedule, calibration records, and qualification status, is not in Phase 3's scope.

Three options were identified in the Phase 3 Implementation Plan §3.3:

- (a) Create a minimal `Equipment` entity now (identity, code, name, `siteId`, a simple status), and extend it in Phase 8 with maintenance and calibration.
- (b) Defer Equipment entirely, recording a free-text equipment reference on each `OperationExecution`.
- (c) Create a `WorkCenter` entity now (a site-owned location or station where an Operation runs), and link Equipment to WorkCenters in Phase 8.

The Phase 3 Implementation Plan §3.3 recorded this as decision D3 (proposed), recommending option (c). The owner has confirmed D3 as proposed. This ADR records that confirmation.

## Decision

1. **Phase 3 implements WorkCenter.** A WorkCenter is a site-owned named location or station at a Site where an Operation runs (for example "Assembly Station 1", "Molding Line A"). It is the Phase 3 execution-location concept.
2. **Equipment, maintenance, and calibration belong to Phase 8.** Phase 3 does NOT create an Equipment entity, does NOT model the `VALID / EXPIRING / EXPIRED / OUT_OF_SERVICE` status, and does NOT model maintenance or calibration records. The full Equipment master arrives in Phase 8 per the PRD §18 roadmap.
3. **The model is designed so future Equipment composes with WorkCenter, not replaces it.** When Phase 8 lands, an `Equipment` entity will be linked to WorkCenters: a WorkCenter may have one or more Equipment items associated with it (`WorkCenter 1:N Equipment`), and an `OperationExecution` may reference the specific Equipment item used (in addition to, not instead of, the WorkCenter). No production-domain restructuring is required at Phase 8: the WorkCenter table, the `Operation.workCenterId` default, and the `OperationExecution.workCenterId` field all remain.
4. **WorkCenter fields (Phase 3).** `code` (unique per site), `name`, `siteId` (required, non-nullable), `description` (optional), `status` (`ACTIVE` or `INACTIVE`). Site-owned: multi-site isolation applies, reusing the Phase 1 `SiteScope` filter and `assertSiteAccess` guard (ADR-0007 pattern). An `INACTIVE` WorkCenter cannot be assigned as the default on a new Operation or selected on a new `OperationExecution` (existing references remain valid for historical traceability).
5. **Operation references a default WorkCenter (optional).** `Operation.workCenterId` is nullable. An Operation may declare a default WorkCenter (the station where it normally runs). `OperationExecution.workCenterId` records the actual WorkCenter used for that execution, and may override the Operation's default (for example, when the default station is busy and the operation runs at an alternate station). The execution-time value is the one used for genealogy.
6. **No Equipment reference is recorded in Phase 3.** `OperationExecution` has no `equipmentId` field in Phase 3. When Phase 8 introduces Equipment, the `equipmentId` column is added to `OperationExecution` (nullable, since historical executions predate Equipment). This is an additive migration, not a restructuring.

### Enforcement

- **Schema.** `WorkCenter` has a compound unique constraint on `(siteId, code)`. `WorkCenter.siteId` is non-nullable with a foreign key to `Site`. `Operation.workCenterId` is nullable with a foreign key to `WorkCenter` (`onDelete: SetNull`; deleting a WorkCenter does not cascade-delete Operations that reference it, but does clear the default). `OperationExecution.workCenterId` is nullable with a foreign key to `WorkCenter` (`onDelete: Restrict`; a WorkCenter that has been used in any execution cannot be deleted, only deactivated, to preserve genealogy).
- **Service-layer guard.** `OperationExecution` create and update paths validate that the chosen `workCenterId` belongs to the same site as the parent Batch (cross-site WorkCenter assignment is rejected with `AuthorizationError`, audited as `production.operationexecution.denied`). Selecting an `INACTIVE` WorkCenter on a new execution is rejected with `StateTransitionError`.
- **Audited.** WorkCenter create / update / deactivate emits `production.workcenter.created` / `.updated` / `.deactivated` `AuditEvent`s. `OperationExecution` create / update emits `production.operationexecution.created` / `.updated` with the `workCenterId` in the event payload, so the genealogy record is auditable (ADR-0005 pattern).
- **Tested.** The production-execution test suite covers WorkCenter assignment and override: an Operation with a default WorkCenter can be executed at a different WorkCenter, the execution records the actual WorkCenter, and an `INACTIVE` WorkCenter cannot be selected on a new execution. Cross-site WorkCenter assignment is rejected (covered by `T-ISOL-03`, the cross-site production isolation test). The execution-recording path is covered by `T-EXEC-01`.

## Rationale

- **WorkCenter is a stable, real manufacturing concept that Phase 3 needs.** Production scheduling, capacity planning, and OEE (Phase 10) all need a "where did this operation run" reference. A WorkCenter (a named station or line at a Site) is that reference. It does not depend on anything Phase 8 has not yet built.
- **A minimal Equipment entity now risks Phase 8 rework.** Option (a) (a minimal Equipment entity with just identity and a simple status) would force Phase 8 to either retrofit maintenance, calibration, and the `VALID / EXPIRING / EXPIRED / OUT_OF_SERVICE` status onto an entity whose shape was decided without those concerns, or to deprecate the Phase 3 entity and migrate. Both are restructuring work. WorkCenter, by contrast, is a different concept (location) that Phase 8 composes with (Equipment at a WorkCenter) rather than replaces.
- **Free-text equipment references break genealogy.** Option (b) (a free-text "equipment" string on each `OperationExecution`) loses the ability to query "all executions at station X" or "all executions that used equipment that later failed calibration". PRD §10 requires Equipment in the genealogy. A free-text field is not a genealogy reference; it is a label.
- **WorkCenter is the right granularity for the Phase 3 question.** Phase 3's question is "where did this operation run?", not "which specific machine, with which maintenance status, ran this operation?". The former is a location question; the latter is an asset-management question. Splitting them along the Phase 3 / Phase 8 boundary keeps each phase's scope honest and avoids pre-empting Phase 8's design.
- **Forward-compatibility is structural, not speculative.** The Phase 8 Equipment entity links to WorkCenter via `Equipment.workCenterId`. An `OperationExecution` in Phase 8 gains an `equipmentId` column (nullable, additive). The WorkCenter reference on `OperationExecution` is retained, because the location where work happened is independently useful (OEE by WorkCenter, capacity by WorkCenter) even after the Equipment reference exists. Nothing in Phase 3's WorkCenter design is discarded at Phase 8.

## Alternatives considered

- **Minimal Equipment entity now (option a).** Rejected. A Phase 3 `Equipment` table with just `code`, `name`, `siteId`, and a placeholder `status` would either (i) use a status enum that Phase 8 then has to widen to `VALID / EXPIRING / EXPIRED / OUT_OF_SERVICE` (a breaking enum migration on a populated table), or (ii) leave status as a free-text field that Phase 8 then has to constrain (a data-cleaning migration). Either path is restructuring work on a populated, audited, genealogy-carrying table, which is exactly the kind of late-phase rework the phasing discipline is meant to avoid. WorkCenter avoids this by being a different concept that Phase 8 composes with.
- **Free-text equipment reference (option b).** Rejected. A free-text field on `OperationExecution` cannot be queried, cannot be related across executions, cannot be linked to maintenance or calibration when those arrive in Phase 8, and does not satisfy the genealogy requirement in PRD §10. Traceability requires a reference to a controlled entity, not a label.
- **Defer the execution-location question entirely to Phase 8.** Rejected. Phase 3 production scheduling, capacity planning, and the execution-record audit trail all need a "where" reference. Deferring it would leave `OperationExecution` without a location dimension, which makes Phase 3 execution records strictly weaker than the PRD §10 genealogy requires, and would force Phase 10 OEE to retroactively reconstruct locations from free text or operator memory.
- **WorkCenter with an Equipment placeholder column now.** Rejected. Adding an `equipmentId` column to `OperationExecution` in Phase 3, before the `Equipment` table exists, would require either a nullable column with no foreign key (which invites orphan references and is hard to validate) or a placeholder `Equipment` table (which is option a, rejected above). The clean phasing is to add `equipmentId` in Phase 8 when `Equipment` exists, as an additive migration.

## Consequences

- **Positive (clean phasing).** Phase 3 gets a stable execution-location concept (WorkCenter) that does not pre-empt Phase 8's Equipment design. Phase 8 composes Equipment with WorkCenter (`WorkCenter 1:N Equipment`) without restructuring the production domain. The two concepts (where work happens, vs which asset did the work and its maintenance/calibration state) are kept separate, which matches how each is used downstream.
- **Positive (WorkCenter is independently useful beyond Equipment).** OEE by WorkCenter (Phase 10), capacity planning by WorkCenter, and "all executions at this station" queries are all answerable from the WorkCenter reference alone, regardless of whether Equipment has been introduced. This means Phase 10 OEE does not have to wait for or depend on Phase 8.
- **Positive (genealogy is preserved without a free-text field).** `OperationExecution.workCenterId` is a foreign key to a controlled, site-owned, audited entity. The genealogy chain in PRD §10 has a real reference at the execution-location level, even before the Equipment dimension is added.
- **Negative / cost (Equipment is not in the Phase 3 genealogy).** Until Phase 8, the genealogy records the WorkCenter where an operation ran, not the specific Equipment item. This means Phase 3 traceability can answer "this execution ran at Assembly Station 1" but not "this execution ran on Machine SN-0042, which was last calibrated on date D". This is an accepted scope boundary: the Equipment dimension of genealogy is a Phase 8 contribution, and Phase 3 records the location dimension. Any recall or trace query in the Phase 3 to Phase 7 window is scoped to WorkCenter.
- **Negative / cost (a future Phase 8 migration adds an `equipmentId` column).** When Phase 8 lands, `OperationExecution` gains a nullable `equipmentId` column. Historical executions (Phase 3 to Phase 7) have `equipmentId = NULL`. New executions (Phase 8 onward) populate it. This is an additive, backward-compatible migration. Queries that join through Equipment must account for the null case.
- **Schema impact.** `WorkCenter` is a new site-owned model with `code` (unique per site), `name`, `siteId`, `description`, `status`. `Operation.workCenterId` is nullable (default station, may be overridden at execution). `OperationExecution.workCenterId` is nullable (the actual station for that execution; nullable to allow executions that genuinely have no station, for example an off-line inspection step). Both reference `WorkCenter` via foreign key. No `Equipment` model and no `equipmentId` column exist in Phase 3.
- **Risk (a site renames or restructures its WorkCenters).** A WorkCenter used in any `OperationExecution` cannot be deleted (`onDelete: Restrict`); it can only be deactivated (`status = INACTIVE`). Deactivation prevents new assignments but preserves historical references. Renaming the `name` field is allowed (it is a label, not a key); renaming the `code` is not (it is the unique-per-site key and is referenced in audit events). Mitigated by: (a) the delete-restriction, (b) the deactivation path, (c) audit-event payloads recording the `workCenterId` (a stable surrogate key) rather than the `code`.
- **Reversibility.** Low for the WorkCenter decision (a WorkCenter table populated with executions cannot be cleanly removed without losing the location dimension of genealogy). High for the Equipment phasing decision (Phase 8 can introduce Equipment at any time; nothing in Phase 3 blocks it). Not planned to reverse either.

## Compliance note

This ADR records an architectural phasing decision: WorkCenter (the location where an Operation runs) is implemented in Phase 3, and Equipment (the asset with maintenance, calibration, and qualification status) is implemented in Phase 8 per the PRD §18 roadmap. The two compose (`Equipment` at a `WorkCenter`) without restructuring the production domain. It is not a claim of ISO 13485 / FDA 21 CFR Part 820 / Part 11 / GxP compliance. The Equipment dimension of traceability genealogy (PRD §10) is a Phase 8 contribution; Phase 3 records the WorkCenter (location) dimension. Compliance depends on intended use, validated configuration, the eventual Equipment master and maintenance/calibration workflows (Phase 8), infrastructure, and evidence (PRD §17).
